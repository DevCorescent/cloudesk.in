What limits capacity

  • Each server process is CPU-bound. During the test the Node server ran at about 143% CPU (its main thread fully busy) while Postgres used about one core. Health checks stayed near 2 ms, so requests were not blocked, just queued.
  • The database pool is not the limit. Raising DB_POOL_MAX from 10 to 25 gave the same 210 req/s. Keep 10.
  • More servers add capacity. Two servers handled 261 req/s against 179 for one, on the same signed-in mix. The gain was 1.5× rather than 2× only because Postgres and the load generator shared the same laptop; on AWS, RDS runs separately.
  • Rate limits held under load. At 200 users, 5 note writes got a 429 because three test accounts were shared by all virtual users (about 8 writes per second per person). Real people stay far below that.

Sizing for launch

  • Plan for about 200 requests per second per 1 vCPU web task with a p95 under 600 ms. A typical signed-in person sends one request every 5–10 seconds, so one task serves roughly 1,000–2,000 people active at the same moment.
  • Run at least 2 web tasks (for availability during deploys) and autoscale on CPU at 60%. Run exactly one worker task.
  • Keep DB_POOL_MAX × tasks + 2 per task under RDS max_connections.
  • The home dashboard is the most expensive call (91 ms when idle). Caching each workspace's dashboard for 30–60 seconds would take the largest load off the database at scale.

Setup: production build (next start, one process) on an Apple M2, 8 cores, 16 GB, with local Postgres. 11 endpoints in a weighted mix (marketing pages, signed-in app pages, dashboard, documents, search, notifications, inbox and note writes), 30 seconds per level, a demo workspace with real invoices, deals and projects. Each virtual user sent from its own address so the firewall saw separate people. All test data was deleted afterwards.

Strong controls found: one request pipeline for sessions, Origin checks, body caps and error masking; workspace checks that answer 404 to non-members; Argon2id passwords; hashed session and code tokens with lockout; SSRF protection that pins DNS and re-checks redirects; sandboxed rendering of user files and email; a Postgres-backed rate limiter; encrypted integration keys; a non-root container; secrets in Secrets Manager. Not reviewed: ZIP/XLSX parser limits, the code sandbox internals, SCIM and API-key handling, guest-chat token lifecycle, and about 130 module routes beyond the sample.

Before go-live

  • Commit and push the code. The repository still has only its first commit and no remote, so the CI and deploy workflows cannot run yet.
  • Set production variables: APP_URL on https, TRUST_PROXY=xff-last, DATABASE_SSL_CA for RDS, a mail provider (sign-up codes and resets need it), APP_ROLE=web on web tasks and exactly one worker.
  • Match the firewall's client-address setting in Admin → Security to TRUST_PROXY, and never set FIREWALL=off.
  • Run 2+ web tasks with CPU autoscaling at 60%, and size RDS max_connections for 10 per task + 2.
  • Add alarms for 5xx rate, p95 latency, task CPU, RDS connections and the rate_limit_store_unavailable log line.
  • Pin the image by digest and confirm RDS automated backups with point-in-time recovery.
  • After launch: nonce-based CSP, sign-up enumeration fix, session idle timeout, dashboard caching.
